# Section 2.4 — Task Relation Learning Approach (Explained)

**Paper:** *A Survey on Multi-Task Learning*, Zhang & Yang (2022), IEEE TKDE

---

## Slide 1: Where This Fits

**Two big families of MTL:**

```
Feature-based MTL:
  "Let's share a representation"
  → One encoder, many task heads
  → wavCSE does this

Parameter-based MTL:
  "Let's constrain how the weights relate to each other"
  → Each task has its own parameters
  → But we penalize them for being too different from related tasks
```

**Within parameter-based, four strategies:**

| Strategy | How tasks relate |
|----------|-----------------|
| Low-Rank (2.2) | The whole weight matrix W is low rank |
| Task Clustering (2.3) | Tasks belong to discrete groups |
| **Task Relation (2.4)** | **Learn a continuous similarity score for each pair** |
| Decomposition (2.5) | Split each task's weights into shared + unique parts |

> **Speaker notes:**
> - The key insight that separates 2.4 from the others: it doesn't force tasks into boxes (clusters) or assume one global structure (low rank). It says "let each pair of tasks have its own similarity score, and learn that score from the data."
> - Think of it as the difference between saying "these three tasks are in group A" (clustering) vs saying "task 1 and 2 are 85% related, 1 and 3 are 30% related, 2 and 3 are 20% related" (task relation learning).

---

## Slide 2: The Core Problem and Solution

**The problem:**
How do you know which tasks should help each other?

**The old answer:** an expert guesses.
- "Keyword spotting and speaker ID are probably related — give them similarity 0.8"
- "Keyword spotting and emotion — maybe 0.3?"

**The new answer (this section):** let the data decide.
- Introduce a matrix **Ω** (Omega) — an m×m table
- Ω_ij = the learned similarity between task i and task j
- Ω is NOT hand-coded — it starts random and gets updated during training
- End result: Ω *is* your answer to "how are these tasks related?"

```
Example with 3 tasks (KS = keyword spotting, SID = speaker ID, ER = emotion):

After training, you might get:
         KS    SID   ER
    KS  [1.0   0.72  0.15]
Ω = SID [0.72  1.0   0.08]
    ER  [0.15  0.08  1.0 ]

Reading: KS and SID are strongly related (0.72).
         Neither is strongly related to ER.
         This was learned — nobody told the model this.
```

> **Speaker notes:**
> - Ω is a covariance matrix, not correlation. The diagonal is each task's variance. I'll normalize to correlation when I show numbers so it's always on a 0-1 scale.
> - The "joint learning" part matters: you don't first guess Ω, then train. You train everything together. As the weights get better, Ω gets better. As Ω gets better, the weights get better. They bootstrap each other.
> - Challenge: for m tasks, Ω has m(m+1)/2 unique entries. For 100 tasks, that's ~5000 numbers to learn. Later methods add sparsity to handle this.

## Slide 3: Before Anyone Learned Ω — The Pre-MTGP Era

Three approaches, all relying on **human-provided** task relationships:

### Approach 1: Uniform — "everyone is equally related"
```
Pull every task's weight vector toward the average of all weight vectors.
One number controls how hard you pull.
```
- Evgeniou et al., 2004

### Approach 2: Pairwise weights — "here's my guess for each pair"
```
Expert gives a number s_ij for each task pair.
Penalty = Σ s_ij × (distance between w_i and w_j)²
If s_ij is large → w_i must be close to w_j
If s_ij is small → no constraint
```
- Evgeniou et al., 2005

### Approach 3: Tree — "tasks are in a taxonomy"
```
Tasks sit in a known hierarchy (like ImageNet's class tree).
Each node's weight is pulled toward its parent's weight.
```
- Kato et al., 2007

**The fatal flaw:** if the expert is wrong, the model is stuck. Bad assumptions → worse than single-task learning.

> **Speaker notes:**
> - Note that these pre-MTGP methods are not stupid — they were the best available at the time. The uniform approach (pull toward mean) is actually a decent baseline: it encodes "if I don't know which tasks are related, I'll assume all of them are, weakly."
> - The pairwise approach is conceptually closest to what MTGP/MTGP/MTRL do, except the s_ij values come from an expert instead of from data. The math of the regularizer is the same: penalize distance between weight vectors, scaled by similarity.
> - The tree approach is the most structured — good when you have a real taxonomy (e.g., recognizing dog breeds). Worthless when tasks don't have a natural hierarchy.

## Slide 4: MTGP — Learning Ω from Data

**Bonilla et al., 2007**

The first method that says: "I will learn Ω from the data, not ask a human."

### Step-by-step intuition:

**1. What's a Gaussian Process?**
Normally you learn weights. A GP skips weights entirely. It directly models the *function* — "what output should I expect for this input?" — and uses a kernel to say which inputs produce similar outputs.

**2. How does MTGP extend this to multiple tasks?**
It defines similarity between ANY two (task, input) pairs as:

```
similarity = (how related are the tasks?) × (how similar are the inputs?)
            =         Ω_ij                 ×        k(x, x')
```

**3. The full picture:**
```
All data points, all tasks → one giant covariance matrix Σ

Σ = (task similarities Ω) ⊗ (input similarities K)

This is a block matrix:
┌─────────────────┬─────────────────┐
│  KS block       │  KS↔SID block   │  ← each block is K scaled by
│  (Ω_KK × K)     │  (Ω_KS × K)     │    the corresponding Ω entry
├─────────────────┼─────────────────┤
│  SID↔KS block   │  SID block      │
│  (Ω_SK × K)     │  (Ω_SS × K)     │
└─────────────────┴─────────────────┘
```

**4. How is Ω learned?**
Because everything is Gaussian, you can mathematically "average over" all possible functions f and get a formula that depends only on Ω. Then gradient ascent over Ω maximizes how well it explains the data.

**Limitation:** You get one Ω matrix. No measure of "how sure are we about these numbers?" → next slide.

> **Speaker notes:**
> - Don't get hung up on the GP math. The key intuition is: Ω controls the off-diagonal blocks. If Ω_ij = 0, those blocks are zero → tasks are completely independent. If Ω_ij is large, those blocks are large → knowing task i's labels helps predict task j's labels.
> - The Kronecker product (⊗) is just a clean way to write "multiply each entry of Ω by the whole K matrix." It's a notational convenience.
> - "Integrating out f" sounds fancy but just means: since f is unobserved anyway, we average over all possible f values weighted by how likely they are. This gives us a function of Ω alone, which we can optimize.

## Slide 5: MTGTP — Adding Uncertainty Over Ω

**Zhang & Yeung, 2010**

MTGP gives you a **point estimate** of Ω — one single matrix. But what if the data equally supports Ω_ij = 0.6 and Ω_ij = 0.9? MTGP picks one and ignores the other.

### The fix: put a prior on Ω itself

```
Instead of:     Find the best Ω
We do:          Find a DISTRIBUTION over possible Ω values
```

Specifically:
```
Ω ~ Inverse-Wishart(ν, C)
```
- This is the standard distribution for covariance matrices in Bayesian stats
- `ν` (degrees of freedom): how strongly we trust our initial guess
- `C` (base matrix): our initial rough guess of Ω

### What this gives you:

| | MTGP | MTGTP |
|---|---|---|
| Ω learned? | Single best matrix | Distribution over matrices |
| Sensitive to noise? | Yes | Less (heavier tails) |
| Can tell you "I'm unsure about relationship X"? | No | Yes |

The heavier tails of the resulting t-process mean: one weird data point won't dramatically change Ω. Practical when some tasks have messy data.

> **Speaker notes:**
> - The Inverse-Wishart is the "conjugate prior" for covariance matrices — meaning the math stays clean. Don't worry about the details; just know that it's the natural choice for putting uncertainty over a covariance matrix.
> - MMD initialization: they pre-compute a rough task similarity from raw features using Maximum Mean Discrepancy. So the model starts with a reasonable guess and refines. This is good engineering — don't start Ω from random noise.

## Slide 6: MTRL — The Central Method

**Zhang & Yeung, 2010, 2012**

MTGP and MTGTP work in "function space" — they model the unknown function directly, with no weight vectors. MTRL shifts to "weight space" — each task has an explicit weight vector w_i.

### The key idea:

Stack all task weight vectors into a matrix W:
```
W = [w₁  w₂  ...  w_m]    ← d features × m tasks
```

Then place a **matrix normal** prior on W:
```
W ~ MN(0, I, Ω)
     │  │   │
     │  │   └── Task relationships (the Ω we want to learn)
     │  └────── Feature independence (each feature dimension treated separately)
     └───────── Zero mean (weights centered at 0)
```

### What this prior means in plain terms:

- Each task's weight vector has its own column in W
- The prior says: "task i and task j should have similar weights, proportional to Ω_ij"
- Features are assumed independent (the identity I) — we're only modeling task-level structure

### The optimization problem:

```
minimize:   [how wrong are predictions] 
          + λ₁ × [size of weights] 
          + λ₂ × [coupling based on Ω]

subject to:  Ω is a valid covariance matrix (positive definite)
             trace(Ω) ≤ 1  (prevents Ω from shrinking to zero)
```

**Key property:** This is **convex** — there's one global optimum. Gradient descent will find it. Unlike MTGP, you won't get stuck in local minima.

> **Speaker notes:**
> - Why switch to weight space? It gives convexity. In function space (MTGP), the marginal likelihood has multiple peaks — you can converge to different Ω depending on initialization. In weight space (MTRL), there's one answer.
> - The trace constraint `tr(Ω) ≤ 1` prevents a degenerate solution: the model would otherwise set Ω → 0, which makes Ω⁻¹ huge, which forces all w_i → 0 (over-regularization). The constraint says "you can't make Ω arbitrarily small."
> - An elegant property: if you fix Ω, the optimization over W splits into m independent problems. You can parallelize across tasks.

## Slide 7: Extensions of MTRL

Once the core MTRL formulation existed, people extended it in many directions:

| Extension | Problem it solves | How |
|-----------|-------------------|-----|
| **Sparse Ω** (Zhang 2017) | Too many pairwise relationships to learn (O(m²)) | Add ℓ₁ penalty on Ω → most entries become exactly 0 |
| **High-order** (Zhang & Yeung 2013) | Pairwise isn't enough — what about 3-way interactions? | Generalize to `(WᵀW)ᵗ ~ Wishart(Ω)` |
| **Block sparse** (Archambeau 2011) | Tasks form groups automatically | Prior favors block-diagonal Ω |
| **Low-rank Ω** (Yang 2013) | Ω is m×m, too big | Force Ω = LLᵀ with L being skinny (m×r, r << m) |
| **Deep learning** (Long 2017) | MTRL was for linear models | Extend to tensor normal prior over neural net weight tensors |
| **Asymmetric** (Zhang 2012) | Similarity might not be symmetric | Learn a directed similarity: A→B ≠ B→A |

**The most interesting one for the FYP:**

The deep learning extension (Long 2017) is the bridge between MTRL and neural networks. Instead of a 2D Ω matrix over task weight vectors, it uses a tensor normal prior over the entire parameter tensor of the last shared layers. This is what you'd need to apply task relation learning to a model like wavCSE.

> **Speaker notes:**
> - The sparsity extension is practically essential. Without it, Ω has m(m-1)/2 free entries. With ℓ₁, most become exactly zero — you only learn the relationships that the data actually supports.
> - The asymmetric variant is philosophically elegant: if you have one task with 10,000 labeled examples and another with 50, the big task should help the small one more than vice versa. Standard MTRL forces symmetry — Ω_ij = Ω_ji.

## Slide 8: How the MTRL Regularizer Actually Works

The term `tr(W Ω⁻¹ Wᵀ)` looks opaque. Here's what it does:

### Case 1: No task relationships
If Ω is just the identity matrix:
```
tr(W · I · Wᵀ) = sum of all w_i²   ← plain L2 weight decay
```
No coupling. Every task trains independently.

### Case 2: Tasks are related (Ω has off-diagonals)
If Ω has structure, Ω⁻¹ has inverse structure:
```
Large Ω_ij  →  Small Ω⁻¹_ij  →  Small penalty for w_i differing from w_j
Small Ω_ij  →  Large Ω⁻¹_ij  →  Large penalty for w_i differing from w_j
```

Wait — this sounds backwards. Let me explain properly:

The math actually works through the *joint* effect. When Ω says "these tasks are related," the optimal W will naturally have similar columns for those tasks, because the regularizer makes it more "expensive" for them to differ *given* the overall structure of Ω. The effect is: related tasks share statistical strength through the regularizer.

### Case 3: Block diagonal Ω
```
        ┌──────┬──────┬──────┐
        │  A   │  0   │  0   │    Group A: KS, SID (related)
Ω =     ├──────┼──────┼──────┤
        │  0   │  B   │  0   │    Group B: ER, emotion variants
        ├──────┼──────┼──────┤
        │  0   │  0   │  C   │    Group C: unrelated tasks
        └──────┴──────┴──────┘
```
Tasks within each block help each other. Tasks across blocks don't interact.

**The practical result:** after training, Ω tells you which tasks actually benefit from each other — learned, not assumed.

> **Speaker notes:**
> - The trace constraint `tr(Ω) ≤ 1` is what prevents Ω from just becoming tiny. If Ω → 0, Ω⁻¹ → ∞, and the penalty dominates → model sets all weights to zero. The constraint caps how small Ω can go.
> - A common confusion: does large Ω_ij mean large or small penalty? Think of it this way: Ω encodes the *allowed* covariance. Large Ω_ij means the model *expects* w_i and w_j to covary — so it doesn't penalize their similarity. But it *does* penalize them for being too independent (since that violates the expected structure).

## Slide 9: The Big Picture — Bayesian Hierarchy

All the methods in this section share the same three-level structure:

```
Level 1:  Observed labels y   ←  What we actually see
              ↑
Level 2:  Latent function f (or weights W)  ←  What we want to learn
              ↑
Level 3:  Task relationships Ω  ←  What ties tasks together
```

The methods differ in **how deep they go**:

| Method | Level 3 (Ω) | Level 2 | Level 1 |
|--------|------------|---------|---------|
| Pre-MTGP | Fixed by expert | W | y |
| MTGP | Point estimate, learned | f (GP) | y |
| MTGTP | Distribution over Ω, learned | f (GP) | y |
| MTRL | Point estimate, learned | W (weights) | y |

### The function-space vs weight-space duality:

For a **linear** kernel, MTGP (function-space) and MTRL (weight-space) are the same model in different clothes. MTRL wins on convexity. MTGP wins on expressiveness with nonlinear kernels.

### Why this matters for the FYP:

wavCSE stops at Level 1 — no Ω at all. It says "all tasks are equally important" (equal weighting). Adding Level 3 (a learned Ω) would tell us quantitatively which speech tasks help each other and which conflict.

> **Speaker notes:**
> - The function vs weight space distinction is important to mention but not to dwell on. The takeaway is: MTRL gives us a clean optimization problem we can solve reliably. MTGP is more expressive but harder to optimize.
> - For extending wavCSE, you'd add an Ω penalty on the task head weight matrix. Since task heads are linear layers, MTRL applies directly — no need for GP machinery.

## Slide 10: How Does This Compare to Other MTL Approaches?

### vs Low-Rank (Section 2.2)

| Low-Rank | Task Relation |
|----------|---------------|
| "W has low rank" | "W's columns are coupled by Ω" |
| One global property | Per-pair relationships |
| Fast to compute | More expressive |

**Connection:** when you constrain Ω to be low-rank (Ω = SᵀS with skinny S), MTRL becomes equivalent to low-rank MTL. So task relation learning is actually the more general framework — low-rank is a special case.

### vs Task Clustering (Section 2.3)

| Clustering | Task Relation |
|------------|---------------|
| "Task 1 and 2 are in the same group" | "Task 1 and 2 have similarity 0.72" |
| Groups are discrete, binary | Similarity is continuous |
| Better when tasks naturally cluster | Better when similarity is a spectrum |

### vs Feature-Based (Section 2.1)

These are **orthogonal, not alternatives**. You can use both:
```
audio → [Shared Encoder] → embedding → Task Head (KS)
                     ↑                  Task Head (SID)   ← add Ω penalty here
              feature-based             Task Head (ER)
                                        ─────────────────
                                        parameter-based
```
Long et al. (2017) does exactly this for deep networks.

> **Speaker notes:**
> - The combination of feature-based + parameter-based is the natural architecture for modern deep MTL. The encoder does the sharing (feature-based). Ω constrains the task heads (parameter-based). You get the best of both.
> - For wavCSE specifically: keep the WavLM encoder (feature-based), but replace EW with a learned Ω on the FC task heads. This would give you quantitative data on KS↔SID↔ER task relationships.

## Slide 11: Summary

**The evolution in one line:** Expert guesses → MTGP (learn Ω) → MTGTP (add uncertainty over Ω) → MTRL (make it convex and practical).

**What Ω actually is:** A table of numbers, one per task pair, that tells you how much two tasks should share information. Learned from data, not assumed.

**Why you'd use this:**
- You want to know which tasks help each other (not just "they all do")
- You have tasks with unequal amounts of data (rich tasks regularize poor ones)
- You need the answer to be interpretable (Ω is a heatmap you can show)

**The catch:**
- O(m²) parameters in Ω — gets expensive with many tasks
- Does not handle outlier tasks automatically — even an unrelated task gets a nonzero Ω entry, and that can hurt all tasks

**FYP connection:**
- wavCSE currently uses equal weighting: `total_loss = loss_KS + loss_SID + loss_ER`
- Task relation learning would replace this with: `total_loss + tr(W Ω⁻¹ Wᵀ)` where Ω answers "how related are KS, SID, and ER?"
- This is a natural next step — and the math is already worked out in this section of the survey.

> **Speaker notes:**
> - The open problem about outlier tasks is directly relevant to the FYP's focus on task imbalance. None of these methods distinguish between "this task is genuinely unrelated" and "this task just has noisy data." A task that's truly an outlier can corrupt Ω, which then degrades all tasks through the coupling.
> - The practical path: if you were to implement this, start with MTRL (convex, simple, well-documented). Use the sparsity extension if you have more than ~5 tasks. Switch to the tensor-variate extension (Long 2017) if you need deep network compatibility.
